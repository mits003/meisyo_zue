# FOSS4G Hiroshima 名所図会マップ — 初期計画書

- 作成日: 2026-06-23
- リポジトリ: `git@github.com:mits003/meisyo_zue.git`
- ステータス: 初版 (initial plan)

## 1. プロジェクト概要

FOSS4G Hiroshima の参加者が **OpenStreetMap (OSM)** から場所を選び、
名前・カテゴリ・タグ・コメントを添えて「おすすめスポット」として投稿できる
軽量な Web 地図アプリ。オープンデータで作る、現代版の *名所図会*。

### 目的

- 参加者がイベント中に気軽におすすめの場所を共有できる場をつくる。
- OSM / FOSS4G の理念に沿って、すべてオープンデータ・オープンソースで構築する。
- ローカル / デモ用途から始め、後から単一ホストへ容易にデプロイできる構成を保つ。

## 2. 現状のアーキテクチャ

| 層 | 採用技術 |
|---|---|
| バックエンド | FastAPI + SQLite (Python、ビルド工程なし) |
| フロントエンド | プレーンな HTML/CSS/JS + Leaflet (CDN 読み込み)、モバイルファースト、英語 UI |
| POI ソース | OpenStreetMap (Overpass API) |
| 地図タイル | OpenStreetMap |

### ディレクトリ構成

```
app/
  config.py      会場座標・地図デフォルト・カテゴリ分類
  db.py          SQLite スキーマ + コネクション
  models.py      Pydantic モデル + バリデーション
  repository.py  pois / posts の CRUD・検索
  poi.py         Overpass 取得 -> pois テーブル (CLI)
  seed.py        デモ用おすすめデータ (CLI)
  main.py        FastAPI アプリ (REST API + 静的配信)
static/          index.html, css/, js/ (Leaflet フロントエンド)
data/            app.db (実行時に生成、git 管理外)
docs/            計画書・設計メモ
```

### API（現状）

| Method | Path | 説明 |
|---|---|---|
| GET | `/api/meta` | カテゴリ分類 + 地図デフォルト |
| GET | `/api/pois?q=&bbox=` | 候補地（投稿フォーム用） |
| GET | `/api/posts?category=&subcategory=&tag=&q=` | おすすめ一覧 |
| POST | `/api/posts` | おすすめを作成 |

### 既知の前提・制約

- ログインなし設計。投稿者名は自己申告（友好的なイベント用途として許容）。
- フィールド長はサーバ側で上限を設定し、軽度の悪用対策とする。
- POI は事前に Overpass で取得し SQLite にキャッシュする方式。

## 3. 今後の改善計画（ロードマップ）

優先度は **P1（早期）/ P2（中期）/ P3（後期）** で示す。

### 3.1 Web 公開のロードマップ 〔P1〕

ローカル / デモから、参加者がスマホから安心して使える公開環境へ。

**ステップ**

1. **デプロイ先の選定**
   - 候補: Fly.io / Render / Railway / VPS (Docker)。
   - SQLite を使う以上、単一インスタンス + 永続ボリュームが前提。
     スケールアウトが必要になった段階で PostgreSQL 移行を検討。
2. **コンテナ化**
   - `Dockerfile`（`uv` ベース）と `docker-compose.yml` を用意。
   - `data/` を永続ボリュームにマウントし `app.db` を保持。
3. **本番設定の分離**
   - 環境変数で会場座標・CORS・ログレベルを切り替え（`app/config.py` を env 対応に）。
   - `--reload` を外し、`uvicorn`/`gunicorn` ワーカー構成で起動。
4. **HTTPS とドメイン**
   - リバースプロキシ（Caddy / Nginx）で TLS を終端、独自ドメインを割当。
5. **基本的な堅牢化**
   - 投稿エンドポイントへのレート制限。
   - 入力バリデーション再点検（XSS 対策として表示時のエスケープ確認）。
   - バックアップ: `app.db` の定期スナップショット。
6. **観測性**
   - アクセスログ / エラーログ、簡易メトリクス（投稿数・POI ヒット率）。

**完了条件**: 公開 URL にスマホからアクセスし、投稿・閲覧・絞り込みが安定動作する。

### 3.2 写真の投稿 〔P1〜P2〕

おすすめスポットに写真を添付できるようにし、視覚的な魅力を高める。

**設計方針**

- `posts` に画像参照（`image_path` または `image_url`）を追加。複数枚は別テーブル
  `post_images(post_id, path, sort_order)` で対応。
- **アップロード API**: `POST /api/posts` をマルチパート対応にするか、
  画像専用の `POST /api/uploads` を新設してから投稿に紐付ける。
- **保存先**:
  - 初期は ローカル `data/uploads/`（公開時は静的配信 + 永続ボリューム）。
  - 将来は S3 互換オブジェクトストレージ（Cloudflare R2 等）へ移行可能に。
- **前処理**: サーバ側でリサイズ・EXIF 除去（位置情報の意図せぬ漏洩を防ぐ）・
  JPEG/WebP 再エンコード。サムネイル生成。
- **制約**: ファイルサイズ上限・MIME 検証・枚数上限。
- **フロント**: 投稿フォームにファイル選択 + プレビュー、詳細カードに画像表示。

**留意点**: 画像の権利・モデレーション方針（不適切画像の通報/削除）を併せて検討。

### 3.3 POI を OSM から動的に取得 〔P2〕

現状の「事前 Overpass 取得 → SQLite キャッシュ」を、地図操作に応じた
動的取得へ拡張し、会場周辺以外でも使えるようにする。

**設計方針**

- フロントの地図移動（`moveend`）で現在の **bbox** を取得し、
  `GET /api/pois?bbox=` をデバウンス付きで呼ぶ。
- バックエンドは:
  1. まず SQLite キャッシュを参照。
  2. 未取得領域なら Overpass へ問い合わせ、結果をキャッシュに追記してから返す
     （read-through cache）。
  3. Overpass のレート制限・障害に備え、タイムアウト / リトライ / フォールバック。
- **キャッシュ戦略**: タイル or geohash 単位で「取得済み領域」を記録し、
  重複問い合わせを抑制。TTL を設けて鮮度を担保。
- **負荷対策**: ズーム閾値（例: zoom 15+）でのみ取得、取得件数の上限、
  Overpass エンドポイントの分散 / 自前ミラー検討。
- **マーカー表示**: 件数増加に備えクラスタリング（`Leaflet.markercluster`）を導入。

**完了条件**: 会場外でも地図を動かすと周辺 POI が自然に表示され、
同一領域の再問い合わせが抑制される。

### 3.4 いいねボタンの追加 〔P2〕

おすすめスポットへの共感を可視化し、人気スポットを浮かび上がらせる。

**設計方針**

- データ: `posts.like_count`（集計値）+ 可能なら `likes(post_id, voter_key, created_at)`
  で重複防止。ログインなし設計のため `voter_key` は
  クッキー / localStorage のランダム ID（厳密な不正防止はしない）。
- **API**:
  - `POST /api/posts/{id}/like` … いいね（トグル）
  - `DELETE /api/posts/{id}/like` … 取り消し
  - 一覧 / 詳細レスポンスに `like_count` と `liked_by_me` を含める。
- **フロント**: 詳細カード / 一覧に ♥ ボタンとカウント、楽観的更新。
- **拡張余地**: いいね数での並び替え・「人気」フィルタチップ、
  マーカーサイズや色への反映。

**留意点**: ログインなしのため厳密なユニーク性は担保できない。
イベント用途として「軽い人気投票」と割り切る。スパム対策はレート制限で補う。

## 5. 横断的な検討事項

- **データモデルの後方互換**: スキーマ変更時はマイグレーション手順を `docs/` に記録。
- **モデレーション**: 写真・コメントの通報 / 削除フロー（公開時に必須化を検討）。
- **プライバシー**: EXIF 位置情報の除去、投稿者名の取り扱い周知。
- **アクセシビリティ / i18n**: 現状は英語 UI。将来的に日本語 UI 切替も検討。
- **テスト**: API の最小限の自動テスト（投稿・取得・いいね）を整備。
